## Протокол итерации агентом

Один этап = одна сессия. Правила, чтобы проходы не размывались:

1. Прочитать этот файл и `REVIEW_FINDINGS.md`, взять первый этап со статусом `todo`.
2. Ревьюить **только** пути этапа. Замеченное вне области — записать одной строкой в раздел
   «Замечено вне области», не расследуя.
3. Находки писать в `REVIEW_FINDINGS.md` со сквозным ID (`F-R1-01`), severity (P1/P2/P3),
   `файл:строка`, одним предложением суть и **конкретным сценарием отказа** (какие входные данные →
   какое неверное поведение). Без сценария это не находка, а мнение.
4. Помечать уверенность: `CONFIRMED` (проверено чтением всех веток кода) или `PLAUSIBLE` (гипотеза).
5. **Не чинить по ходу.** Исключение — P1 с явного разрешения. Фиксы идут отдельным проходом после
   утверждения списка, чтобы ревью не превращалось в рефакторинг вслепую.
6. В конце: сборка должна проходить (`:app:assembleDebug`), статус этапа → `done`, краткое резюме
   в 3–5 строк в конце секции этапа.
7. Потолок — 12 находок за проход. Больше — значит, ранжировать и оставить лучшее.

### Шаблон запуска

```
Прочитай docs/CODE_REVIEW_PLAN.md и docs/REVIEW_FINDINGS.md.
Выполни этап <R2>: ревью по правилам протокола, только пути этого этапа.
Находки допиши в REVIEW_FINDINGS.md, статус этапа обнови. Ничего не чини.
```

Механическую часть этапа можно предварительно снять встроенной командой — она даёт баги и
упрощения, агент сверху добавляет архитектурное суждение:

```
/code-review high app/src/main/java/com/drklo/pomodoro/timer
```

### detekt (+ форматирование)

Ловит то, чего Android Lint не видит: сложность, длину функций, дублирование, code smells.
`detekt-formatting` оборачивает ktlint, поэтому отдельный ktlint-плагин не нужен.

```kotlin
// build.gradle.kts (корень)
plugins { id("io.gitlab.arturbosch.detekt") version "1.23.x" apply false }
```
```kotlin
// app/build.gradle.kts
detekt {
    buildUponDefaultConfig = true
    config.setFrom(rootProject.file("config/detekt.yml"))
    baseline = rootProject.file("config/detekt-baseline.xml")
}
dependencies { detektPlugins("io.gitlab.arturbosch.detekt:detekt-formatting:1.23.x") }
```

Оговорка: ветка detekt 1.23.x собрана под Kotlin 1.9, проект на 2.0.21. Обычно работает, но при
включённом type resolution возможны сюрпризы — начинать без него, версию сверить перед подключением.

Опционально для Compose-тяжёлого проекта: ruleset `compose-rules` (правила про state hoisting,
параметры `Modifier`, стабильность) — координаты уточнить перед добавлением.

## R1 — Ядро таймера

Статус: `done` (11.08.2026 — находки `F-R1-01…09` в журнале)
Пути: `timer/` (7 файлов, 730 строк; `TimerEngine.kt` — 380, самый большой файл проекта)

Самая высокая цена ошибки: баг здесь = потерянная помидорка, то есть потерянные данные пользователя.

Что искать:
- **Жизненный цикл**: `TimerService` как foreground service. Потеря текущего интервала при смерти
  процесса — **намеренная** (README, «Notes»), багом не заводить. Проверять другое: выполняется ли
  обещание из той же строки — «счётчик выполненного за день восстанавливается».
- **Точность**: `SystemClock.elapsedRealtime()` (строки 168, 202, 221, 306) против сна устройства
  и Doze. Тик через `delay()` — накапливается ли дрейф, корректно ли считается остаток.
- **Гонки**: `_state` (StateFlow) и `tickJob`/`idleJob` меняются из UI-потока и из корутин
  `scope`. `settings` помечен `@Volatile` — проверить, все ли общие поля защищены аналогично
  (`deadlineElapsed`, `sessionDayKey`).
- **Ровно один раз**: запись лога помидорки (строка ~352, `System.currentTimeMillis()`) —
  возможна ли двойная запись при быстром pause/resume или смене фазы; возможна ли потеря.
- **Смена настроек на лету**: `refreshActiveProject` при RUNNING/PAUSED, смена длительностей,
  границы «конца дня» посреди сессии (`sessionDayKey`).
- **Свежий код**: «Seek mode» (коммит `b54fe57`) — перемотка внутри интервала, взаимодействие с
  `deadlineElapsed`.

**Критерий готовности:** каждая ветка `when (status)` пройдена глазами; сценарии «процесс убит»,
«устройство спало 2 часа», «пользователь сменил проект на паузе» — либо описаны как работающие,
либо превращены в находки.

### T2 — Шов времени ✅ выполнено в W2 (условие для тестов R1)

`TimerEngine` уже принимает зависимости через конструктор, включая `scope` — то есть в тест можно
передать `TestScope` с виртуальным временем. Мешает одно: время берётся из статики Android
(`SystemClock.elapsedRealtime()` в 4 местах и `System.currentTimeMillis()` при записи лога).

Ввести узкий порт и передавать его в конструктор:

```kotlin
interface TimeSource {
    fun elapsedRealtimeMs(): Long   // монотонное, для дедлайна
    fun wallClockMs(): Long         // стенные часы, для меток лога
}
```

Дефолтная реализация в `AppContainer`, фейк — в тестах. После этого проверяемо: тик и досрочное
завершение, поведение после «скачка» времени (сон устройства), запись ровно одного лога на
помидорку, переходы фаз, длинный перерыв по интервалу.

### T3 — Порты вместо конкретных классов (движок ✅ выполнен в W2, вьюмодели — в W10)

`SettingsRepository` (тянет `Context` + DataStore) и `TimerEffects` (звук/вибрация) — конкретные

# Заметки по проверке на устройстве

Инструменты, отработанные в этой сессии. Использовать при проверке пакетов, не изобретать заново.

## ⚠️ Инструментальные тесты стирают данные на устройстве

`:app:connectedDebugAndroidTest` после прогона **деинсталлирует** и приложение, и тестовый APK —
штатное поведение AGP. Вместе с APK Android удаляет данные: база помидорок и DataStore-настройки
исчезают. Проверено на практике 14.08.2026: потеряли боевую базу, восстановили из снятого за пять
минут до этого снимка.

Правило: **перед `connectedAndroidTest` на телефоне с боевыми данными — обязательный бэкап.**

```powershell
# Снять (bash, не PowerShell: PS портит бинарный поток при редиректе)
adb exec-out run-as com.drklo.pomodoro cat databases/pomodoro.db > backup.db
adb exec-out run-as com.drklo.pomodoro cat databases/pomodoro.db-wal > backup.db-wal
adb exec-out run-as com.drklo.pomodoro cat files/datastore/settings.preferences_pb > backup.pb

# Склеить WAL в самодостаточный файл: python -c "sqlite3.connect('backup.db').execute(\"VACUUM INTO 'restore.db'\")"

# Вернуть (после переустановки и одного запуска, чтобы создались каталоги)
adb shell am force-stop com.drklo.pomodoro
adb push restore.db /data/local/tmp/restore.db
adb shell run-as com.drklo.pomodoro cp /data/local/tmp/restore.db databases/pomodoro.db
adb shell run-as com.drklo.pomodoro rm -f databases/pomodoro.db-wal databases/pomodoro.db-shm
```

Лучший вариант — гонять инструментальные тесты на эмуляторе, а телефон держать для ручных сценариев.

**Сборка и установка** (`$env:JAVA_HOME` — JBR из Android Studio):
`.\gradlew.bat :app:assembleDebug` → `adb install -r app\build\outputs\apk\debug\app-debug.apk`.

**Чтение базы приложения.** Только `exec-out`, иначе файл приезжает пустым или битым:
```
adb exec-out run-as com.drklo.pomodoro cat databases/pomodoro.db     > pomo.db
adb exec-out run-as com.drklo.pomodoro cat databases/pomodoro.db-wal > pomo.db-wal
```
Забирать **вместе с WAL** — без него свежие записи не видны. Разбирать python-модулем `sqlite3`;
путь python передавать в windows-виде, git-bash путь он не откроет.

**Настройки** лежат в `files/datastore/settings.preferences_pb`; ключи и значения видны обычным
поиском печатных строк, `12 02 08 01` — булево `true`.

**Состояние таймера снаружи:** текст уведомления читается из `system_server` и приложение не будит —
`adb shell dumpsys notification --noredact | grep -A40 "pkg=com.drklo.pomodoro"`. Отсюда же видно,
жив ли foreground-сервис: `adb shell dumpsys activity services com.drklo.pomodoro`.

**Doze:** `dumpsys battery unplug` → `dumpsys deviceidle enable` → `force-idle`; возврат —
`unforce`, `disable`, `battery reset`. Помнить: `force-idle` включает ограничения Doze, но **не**
усыпляет процессор; настоящий сон проверяется только без кабеля.

**Грабли.** Отключение кабеля сбрасывает авторизацию отладки — при возврате телефон спросит
подтверждение заново. Устройство само запирается, а при `deviceLocked=1` тапы не проходят.
`TimerService` не экспортирован, запустить таймер через `am` нельзя — только тапом по циферблату.
`alwaysOnDisplay` включён, экран гасить принудительно (`input keyevent KEYCODE_SLEEP`).

## Формат находки

```markdown
### F-R1-03 · P2 · CONFIRMED
**Файл:** `timer/TimerEngine.kt:306`
**Суть:** одно предложение — в чём именно дефект.
**Сценарий:** конкретные входные данные и состояние → конкретное неверное поведение.
Например: «интервал 25 мин, устройство спало 40 мин, при пробуждении остаток показан
отрицательным вместо перехода к следующей фазе».
**Статус:** open | fixed (коммит) | wontfix (причина)
```

Severity: **P1** — пользователь это видит или теряет данные. **P2** — сломается при следующем
изменении рядом (дублирование, гонка, O(n²)). **P3** — единообразие, читаемость, косметика.
